# oneform: чтение форм и правка текста модулей (стабильный режим)

Инструмент `oneform` (Rust CLI, `oneform.exe`) раскладывает форму в `Form.xml` + `FormModule.bsl` и упаковывает правки модулей обратно,
сохраняя всё, что не менялось. Подробности: `docs/agent-guide.md` в репозитории oneform-1c; допустимые теги по типам
элементов: `docs/xml-reference.md`.

**Правило для агента.** По умолчанию работайте в стабильном режиме: читайте формы, правьте текст модулей, делайте ревью. **Не используйте экспериментальные функции по своей инициативе — даже чтобы «закончить задачу».** Если задаче нужна запись раскладки (добавить поле или кнопку, перенести элемент, сменить шрифт, создать форму и т. п.), остановитесь и: (1) объясните, что нужно сделать; (2) назовите риск простыми словами: форма может перестать открываться в 1С; (3) предложите варианты: пользователь делает это в Конфигураторе, либо вы готовите описание изменения; (4) продолжайте только после того, как пользователь **явно подтвердит в текущем разговоре**, что понимает: это экспериментальная функция, она может сломать форму. Общая задача вроде «сделай форму красивее» подтверждением **не является**. С подтверждением работайте по навыку `oneform-forms-experimental`; здесь запись раскладки не описана.

**Стабильно:** `extract` (`Form.xml`, `FormModule.bsl`, `ObjectModule.bsl`, а `FormPreview.html` — как дополнение для чтения и ревью), `validate`, `lint`, `preview`, `check`, `diagnose`, `history` (list / diff / restore), `feedback` и правка **текста** модулей (`FormModule.bsl`, `ObjectModule.bsl`) с записью через `pack`; после записи всё равно откройте форму в 1С.

**Экспериментально (флаг `--experimental`):** любое изменение, при котором `pack` перезаписывает поток формы по правкам `Form.xml`, запись `FormStream.bin` и шаблонов, команды `new-form` и `clone-form`. Без флага `pack` пишет только текст модулей; если в плане есть и другое, он отказывает целиком до записи (`EXPERIMENTAL_REQUIRED`, код 2) и перечисляет, что было бы записано; `pack --dry-run` работает без флага и печатает строку `EXPERIMENTAL:`. Не добавляйте флаг сами: при `EXPERIMENTAL_REQUIRED` остановитесь и действуйте по правилу выше.

## Цикл

1. **Перед работой** `oneform validate <каталог> [--json]` — решает по каждой форме `IN_SCOPE` или `OUT_OF_SCOPE` с кодами причин (`format-8.0`, `metadata-layout`, `unsupported-control`, `duplicate-name`, `round-trip-differs`, `stale-projection`, `unreadable`) и ничего не пишет; код выхода 0 — все формы в области, 1 — есть вне области. `IN_SCOPE` — форму можно читать и править текст её модуля. Форму `OUT_OF_SCOPE` не правь через `oneform`: открой её в Конфигураторе (`stale-projection` лечится повторным `oneform extract`). `duplicate-name` форму из области не выводит, но раскладку (`Form.xml`) такой формы править нельзя (`pack` откажет), а `ЭлементыФормы.<Имя>` в её модуле неоднозначно для повторяющихся имён.
2. `oneform extract <каталог>` — создаёт `src/Forms/<Форма>/Form.xml`, `FormModule.bsl`, `FormPreview.html`.
3. Читайте `Form.xml` и правьте `FormModule.bsl` (и `ObjectModule.bsl`). Правила чтения:
   * нет тега = «не трогать»; значение по умолчанию в файле не показывается; бинарные служебные блоки (`raw`/`sig`, `*Record`) в XML не выводятся, если встретились (`extract --carriers`) — не править;
   * `FormModule.bsl`: кодировка, BOM и переводы строк сохраняются как были (Бух. — UTF-8 с BOM, свой BOM не нужен); реквизиты объекта в модуле обычной формы доступны по имени (`Организация`, `Валюта`; `ДокументОбъект.Валюта` тоже), элементы — `ЭлементыФормы.Имя`. Процедуры и функции должны стоять **перед** операторами тела модуля (раздел «ОПЕРАТОРЫ ОСНОВНОЙ ПРОГРАММЫ»): процедуру, дописанную в конец модуля с телом, `pack` отказывает (`bsl-procedure-after-body`) — вставьте её перед первым оператором вне процедур;
   * следы `src/`, `.oneform/`, `.extract-work/` в каталоге выгрузки конфигурации: в список частичной загрузки они не входят (проверено), полную загрузку каталога с ними не проверяли — не включайте их.
4. `oneform pack <каталог> --dry-run` — проверка без записи: список правок (строка `edit …`), ошибки и строки `warning …` (они `pack` не блокируют; `… updated in place` на Windows — каталог держала другая программа, файлы обновлены внутри него). Если в выводе есть строка `EXPERIMENTAL:` или `pack` отвечает `EXPERIMENTAL_REQUIRED` — в плане есть правки раскладки: остановитесь (правило выше), верните правки `Form.xml` (из git или копии) и упакуйте только модуль.
5. `oneform pack <каталог> --backup` — запись текста модулей (первый `pack` файла — всегда с `--backup`). `oneform check <каталог>` — проверка актуальности `src/`.
6. После каждой записи формы открой форму в 1С (или попроси пользователя); `oneform preview` даёт офлайн-превью (`FormPreview.html`, `.oneform/index.html`).
7. **Ревью.** `oneform lint <каталог> [--json] [--strict]` проверяет раскладку (элемент за краем формы, пересечения, растягивание, нижняя панель, порядок обхода) и ничего не пишет; `FormPreview.html` показывает форму приближённо. Числа и рецепты оформления по видам форм — навык `oneform-form-design`; чтобы применить правки раскладки, нужен экспериментальный режим.

## Форма из выгрузки конфигурации: рецепт и история

Изменить модуль формы справочника, документа или обработки из выгрузки конфигурации — по пошаговому рецепту `docs/agent-guide.md`, «Изменить форму из выгрузки конфигурации» (`validate` → `extract` → правка модуля → `pack --dry-run` → `pack` → частичная загрузка со списком из ВСЕХ форм объекта, без `src/`, `.oneform/`, `.extract-work/` → открыть форму → при ошибке откат). Каждый `pack` сам сохраняет прежнее состояние в `<каталог объекта>/.oneform/history/<id>/` и печатает `history <id>` (последние 20, `ONEFORM_HISTORY_KEEP=N`, `0` — выкл.; git не нужен). `oneform history <каталог>` — список снимков; `oneform history restore <каталог> <id> [--dry-run] [--replace-generated]` — вернуть прежнюю форму (текущая сначала сохраняется новым снимком; при неупакованных правках в `src/` отказ; флаг `--experimental` откату не нужен). `--backup` по-прежнему пишет `.bak` и от истории не зависит.

## Изменения форм выгрузки конфигурации в git: `export-forms`

Когда нужно видеть изменения форм между релизами конфигурации в git (бинарный `Form.bin` в `git diff` не читается): `oneform export-forms <выгрузка> --out <папка> [--check]` (стабильно, только чтение; выгрузка не меняется). В `--out` на каждую обычную форму пишутся ровно `Form.xml` и `FormModule.bsl` по пути формы без `Ext/Form.bin` и без `src/` (`<Тип>/<Объект>/Forms/<Форма>/`, `CommonForms/<Имя>/`) и маркер `.oneform-export.json`; запись детерминирована, неизменные файлы не переписываются, исчезнувшие формы удаляются. `--check` ничего не пишет и даёт код 3 при расхождениях. Предупреждения:

* `Form.xml` нулевого размера — формы, для которой проекции нет (формат 8.0, неизвестная раскладка): модуль выгружен, причина в маркере; это не сбой (код 0). Код 1 — какая-то форма не прочитана (остальные выгружены), код 2 — небезопасные пути или лишние флаги.
* **Не запускайте `preview`, `lint`, `pack` и `check` на папке `--out`:** `preview` запишет `FormPreview.html` в отслеживаемое дерево, а папка не `src/` и не источник для `pack`. Для правки формы — `extract` по выгрузке.
* Остальные команды не изменились. Подробно: `docs/agent-guide.md`, «Формы выгрузки для git: `export-forms`».

## Сравнение контейнеров 1С: `container-entries`, `container-diff`

Когда нужно доказать, какие объекты изменились между двумя `.cf` или после слияния конфигураций платформой: `oneform container-entries <файл> [--json]` (записи, раскладка, SHA-256) и `oneform container-diff <A> <B> [--by stored|inflated] [--owners <выгрузка>]... [--expect-owners <файл>] [--json]` (стабильно, только чтение; принимают файлы `.cf`, `.cfe`, `.epf`, `.erf`, не каталоги). Код `container-diff`: 0 — различий нет (или только ожидаемые владельцы), 3 — есть различия, 1 — сбой, 2 — использование. Программа сообщает факты, вывод делает вызывающий. Остальные команды не изменились. Подробно: `docs/agent-guide.md`, «Сравнение контейнеров 1С».

## Отказ, неверное предупреждение, форма не открылась в 1С

`oneform diagnose [PATH]` (ничего не пишет): последние отказы и предупреждения из `.oneform/diagnostics.jsonl` (без содержимого файлов), последний снимок, `validate`, нужный раздел `docs/agent-guide.md` или `docs/experimental-form-editing.md` и готовые команды. `oneform history diff [PATH] [id]` показывает, что изменил последний `pack`. Затем отчёт разработчику `oneform`: `oneform feedback add --history <id> --1c-error "<точный текст ошибки 1С>" --note "<что пробовали>"` (`--kind wish` — пожелание; `--no-files` — без файлов; `--include-binaries` — с `Form.bin`/`.epf`, только по просьбе). Скажите пользователю путь отчёта из вывода. Текст модулей в чаты не вставляйте: в отчёте есть `Form.xml` и `FormModule.bsl`, а в модулях бывают токены и пароли. С `ONEFORM_FEEDBACK_DIR` отчёт копируется и в этот каталог. Правило при работе в репозитории (`.oneform/` и `.extract-work/` в `.gitignore`): `validate` до работы, открыть форму в 1С после каждого `pack`, при отказе — `diagnose` и `feedback add`. Подробно: `docs/agent-guide.md`, «Цикл разработки в репозитории и обратная связь».

## Отказы стабильного режима

Сообщение содержит причину и элемент. Частые: `EXPERIMENTAL_REQUIRED` (в плане есть запись раскладки; флаг не добавлять без подтверждения пользователя), `bsl-procedure-after-body`, `warning: history snapshot not saved`, `history restore`: `src/ has unpacked edits`, формы формата 8.0 (`layout unsupported`, только модуль). Остальные отказы — это отказы правки `Form.xml` (`FORM_EDIT_REJECTED`, `unsupported-*`), они относятся к экспериментальному режиму: таблица в `docs/experimental-form-editing.md`, навык `oneform-forms-experimental`. Таблица стабильных отказов — в `docs/agent-guide.md`.

## Формы старой версии потока (25 / 26)

Часть форм УТ 10.3 читается и допускает правку модуля без ограничений; добавлять в них элементы (экспериментальный режим) можно только `Label`, `InputField`, `CheckBox`, `Button`. Что говорить пользователю — `docs/agent-guide.md`, «Форма старой версии потока (25 / 26): что сказать пользователю»; не конвертируйте форму самостоятельно.

## Внешний отчёт (`.erf`)

Бинарный `.erf` `oneform` не читает: команды пропускают файл и пишут «внешний отчёт: выгрузите в XML (erf-dump), oneform работает с
XML-выгрузкой». Сделайте `erf-dump` в каталог, затем `oneform extract` / правка модуля / `pack`, затем `erf-build`.

# oneform для ИИ-агента: правка и создание обычных форм 1С через XML

`oneform` превращает бинарную обычную форму (внешняя обработка `.epf`, `Ext/Form.bin` выгрузки конфигурации или XML-выгрузки внешнего отчёта через `erf-dump`; бинарный `.erf` не читается, см. «Внешний отчёт (`.erf`)» ниже)
в `Form.xml` + `FormModule.bsl`, а изменённые файлы упаковывает обратно, не трогая ничего, что вы не меняли.
Конфигуратор для работы с элементами не нужен.

## Цикл работы

```bash
oneform extract <PATH>            # рядом с каждой формой появляется src/Forms/<Форма>/Form.xml, FormModule.bsl, FormPreview.html
# правите Form.xml и/или FormModule.bsl
oneform pack <PATH> --dry-run     # полная проверка без записи: список правок или понятная ошибка
oneform pack <PATH> --backup      # запись (.bak хранит прежний файл); первый `pack` файла делайте с `--backup`
oneform check <PATH>              # src/ соответствует бинарнику? (код 0 — да, 3 — нет)
oneform preview <PATH>            # обновить FormPreview.html и .oneform/index.html (офлайн-превью формы)
oneform lint <PATH>               # проверить раскладку Form.xml (замечания error/warning/info; ничего не пишет)
oneform validate <PATH>           # можно ли править форму через oneform: IN_SCOPE / OUT_OF_SCOPE с причинами; ничего не пишет
```

## Область применимости: `oneform validate`

Форма **в области применимости** (`IN_SCOPE`) тогда и только тогда, когда она обычная формата 8.2/8.3, в ней нет неподдерживаемых видов элементов (`ActiveXControl` и т. п.), имена элементов уникальны, она без правок проходит путь «поток → `Form.xml` → поток» байт в байт, а её проекция `src/` актуальна. Иначе — `OUT_OF_SCOPE`: правьте такую форму в Конфигураторе. Формы формата 8.0, формы с `ActiveXControl` и формы с дублями имён элементов вне плана навсегда (решение владельца 28.10.2026): поддержки не будет.

`oneform validate <PATH> [--json]` решает это по каждой форме, не пишет ни одного файла (ни `src/`, ни блокировок) и работает по бинарным исходникам (`Ext/Form.bin`, `.epf`) в памяти; печатает `<объект>/<форма>: IN_SCOPE` или `OUT_OF_SCOPE код[,код] — подсказка`, затем `N forms, M in scope (P %)` и разбивку по причинам; `--json` — массив `{object, form, in_scope, reasons:[{code,hint}]}`. Код выхода: 0 — все формы в области, 1 — есть вне области, 2 — ошибка вызова. Запускайте перед правкой.

| Код | Причина | Что делать |
|---|---|---|
| `format-8.0` | корень потока старше 24 (платформа 8.0/8.1): `Form.xml` не строится, доступен только модуль | Конфигуратор |
| `metadata-layout` | поток не разбирается или имеет неизвестную раскладку (`METADATA_LAYOUT_UNSUPPORTED`, повторный `id`) | Конфигуратор |
| `unsupported-control` | элемент вида без образца (`ActiveXControl`) или с неизвестным GUID | Конфигуратор |
| `duplicate-name` | два элемента с одним именем (как `duplicate-name` в `lint`; `pack` такую форму отклоняет) | уникальные имена в Конфигураторе |
| `round-trip-differs` | `Form.xml` без правок не возвращается в тот же поток (планировщик `pack` отказывает или меняет байты) либо контейнер формы не переживает пересборку | Конфигуратор |
| `stale-projection` (не выводит из области: форма `IN_SCOPE (run extract)`) | `src/` выгружен из другого `Form.bin`/`.epf` или `Form.xml` старой версии (`stale-form-xml`); правки `Form.xml` и `FormModule.bsl` устареванием не считаются; без `src/` причины нет | `oneform extract` заново |
| `unreadable` | объект не читается (битый контейнер, `.epf` с управляемой формой) | починить источник |

Один проход «без правок» — это путь `pack` без изменений: проекция читается обратно, сверяется с потоком по идентификатору, имени, виду и родителю каждого элемента, сравнивается с собой, пустой план применяется, результат сверяется с оригиналом. Свойства элементов он не пересчитывает, поэтому `IN_SCOPE` не отменяет отказов `pack` на конкретной правке.

`lint [--json] [--strict]` находит элемент за краем формы, дубли имён и `id`, пересечения, поля и таблицы, которые не растягиваются, привязку `top="Top" topOffset=K` при `Top` ≠ K (`anchor-mismatch`: сдвинули элемент, а `Anchors` оставили; то же для `left`, `bottom="Top"`, `right="Left"`), нижнюю панель не на `Top = Height − 25`, обход против чтения и отклонения от обычных значений вида формы (поля 8, высоты 19, панели 25); код выхода 1 при `error`, 3 с `--strict` при `warning`. Числа и рецепты по видам форм — `docs/form-design-standards.md` и навык `skills/oneform-form-design/SKILL.md`.

`pack` — транзакция: либо упаковано и проверено, либо файлы не тронуты. Проверка в `pack`: поток правится «на месте»
(байты вне разрешённых диапазонов сохраняются), затем форма декодируется заново и сверяется с вашим XML; для
добавленных/удалённых элементов дополнительно проверяется согласованность привязок (`Anchors`). `pack --dry-run` и `pack`
печатают по строке `edit …` на каждую правку (изменённый элемент и его свойства, `add`, `remove`, `form size`, …) и строки `warning …`.

## Предупреждения `pack` (не блокируют упаковку)

`pack --dry-run` и `pack` печатают `warning <Form.xml>: …`; прочитайте их до того, как отдавать форму в 1С. Упаковка при предупреждении проходит — решать вам.

| Текст | Что делать |
|---|---|
| `removed control 'Имя' is still referenced at FormModule.bsl:N: <строка>` (также `removed page`, `renamed control 'Старое' (now 'Новое')`, `renamed page`; то же для `ObjectModule.bsl` объекта) | в модуле остался `ЭлементыФормы.Имя`, `Элементы.Имя`, `ЭлементыФормы["Имя"]` или `Страницы.Имя` (комментарии и строковые литералы пропускаются); исправьте код. До 20 строк на элемент, дальше `… in +N more lines` |
| `procedure X belongs to removed control 'Имя' (FormModule.bsl:N): remove it, it is an orphan` | обработчик удалённого элемента (по имени из его `<Events>` или `<Имя>ПриИзменении` / `Нажатие` / `НачалоВыбора` и т. п.) остался в модуле; удалите процедуру, если она больше не нужна |
| `field 'Имя' is bound to 'Корень.Реквизит' but its value type could not be resolved; it keeps the template type (ValueList) — give <ValueType kind=... refGuid=...> explicitly or run from a directory next to the configuration export` | тип реквизита неизвестен (нет схемы объекта, составной или неизвестный тип): поле осталось со списковым типом донора; задайте `<ValueType>` или запускайте `pack` рядом с выгрузкой конфигурации |
| `control 'Имя' extends beyond its container (right edge N is beyond the width W of the form): move the control to Left N or enlarge …` | добавленный или сдвинутый элемент выходит за форму или страницу (то же правило, что `outside-container` в `lint`; проверяются только добавленные и изменённые по геометрии элементы); сдвиньте или увеличьте контейнер |
| `button 'Имя' of 'Панель' calls the procedure 'X', which FormModule.bsl does not declare` | процедуры кнопки нет в модуле; допишите её |
| `panel 'Панель': ShowTabs changes the page 'Страница' from WxH to W2xH2; controls beyond the new page area: 'Имя' (right edge N > width W2, bottom edge M > height H2); enlarge the panel by 2 x 20 px (the tab strip) or move and shrink these controls` | `ShowTabs` 0 → 1 у существующей панели с наполнением: закладки отнимают у страниц 2 px по ширине и 20 px по высоте, элементы страницы остаются на местах и могут выйти за страницу (`lint`: `outside-container`). Перечислены только элементы, которые влезали в прежнюю страницу и не влезают в новую (размер панели, который вы меняете в том же `pack`, учтён). Увеличьте панель на 2 × 20 px (и пересчитайте её `Anchors`) или сдвиньте / уменьшите перечисленные элементы; `pack` не отказывает |

Автопривязка добавленного элемента (`Anchors` не написан) берёт **ближайшего соседа** по правленому `Form.xml`: верх — к нижней стороне элемента выше, левый край — к правой стороне элемента слева. Это не всегда тот элемент, к которому вы хотели привязать (соседом может оказаться подпись или лишнее поле). Проверьте результат `lint` и `extract`, а если привязка важна — пишите `<Anchors>` явно.

## Как читать Form.xml

* **Отсутствие тега = «не трогать»**, а не «значение по умолчанию». Чтобы изменить свойство, поставьте тег со
  значением; удалить свойство нельзя — задайте нужное значение.
* **Свойства показаны разреженно**: тег есть, только если значение отличается от значения свежедобавленного элемента
  того же типа. Задали значение по умолчанию — после `pack` тег исчезнет из файла, это не ошибка.
* **Список допустимых тегов для типа элемента** — `docs/xml-reference.md`.
* **Служебных бинарных блоков в `Form.xml` нет** (по умолчанию): `Form.xml` содержит только читаемые свойства. Копии
  бинарных записей (`raw`/`sig`, `InfoRecord`, `Appearance`, `PanelRecord`, `FormRecord`, `ColumnProps`, `GeometryFlags`,
  `RowSource`) нужны только компилятору форм и выводятся ключом `oneform extract --carriers`; `pack` их игнорирует,
  если они есть, и не правьте их.
* `reconstructionComplete="false"` в корне — норма: не все свойства формы описаны в XML (см. выше).
* Порядок элементов в `ChildItems` — по `ZOrder`. `ZOrder` и `TabOrder` считаются в пределах страницы (`Page`) панели, а не всей формы.

## Типовые операции

| Задача | Как |
|---|---|
| Изменить заголовок, размер, положение, видимость, шрифт, цвет, флаги | Поменять тег элемента (`Caption`, `Left`, `Top`, `Width`, `Height`, `Visible`, `Font`, `TextColor`, …) |
| Размер шрифта | `<Font bold="true" size="12"/>`; атрибуты `italic`, `underline`, `strikeout`, `scale` сохраняются |
| Обработчик события | В `<Events>` элемента: `<Click id="0">ИмяПроцедуры</Click>`; тело процедуры — в `FormModule.bsl` |
| Добавить элемент | Новый элемент нужного типа с уникальным `name`, любым свободным `id` (будет пересчитан), `Left/Top/Width/Height`, `ZOrder` (= следующий свободный среди соседей) и `TabOrder` (= следующий свободный на той же странице; у элементов страницы панели обе нумерации идут заново на каждой странице: `ZOrder` 0…k-1, `TabOrder` 1…k); поместить в конец `ChildItems` нужной страницы/панели |
| Панель со страницами | Новый `<Panel name id>` с `Left/Top/Width/Height`, `ZOrder`, `TabOrder`, `<ShowTabs type="ShowTabs" member="Top" code="1"/>` (код `1` — закладки сверху, `0` — без закладок, без тега — `1`; другие коды — отказ `unsupported-panel`) и `<ChildItems>`, где на каждую страницу (хотя бы одну) идёт `<Page name="…"><Title><Item language="ru">…</Item></Title><ChildItems>…элементы…</ChildItems></Page>`. Панель строится «с нуля»: содержимого донорской панели (таблицы, командной панели, события) нет. `Left/Top/Width/Height` страницы не пишите: область страницы выводится из размера панели (с закладками `1, 19, Width-2, Height-20`, без закладок `0, 0, Width, Height`; написанное иначе — отказ `unsupported-panel`, минимальный размер с закладками 9×27). Координаты элементов страницы — от левого верхнего угла области страницы. **`ZOrder` и `TabOrder` считаются на каждой странице отдельно**: `ZOrder` 0…k-1 (повтор на странице — отказ), `TabOrder` 1…k. Привязки элементов страницы: к панели (`top="Top"`, `left="Left"` … — цель `0`) и к элементам той же страницы; без `<Anchors>` элемент вешается на ближайших соседей страницы, как обычно; привязка к элементу вне панели или другой страницы — отказ. Панель можно вложить в страницу новой панели. Панель из одной страницы без закладок и без элементов `extract` показывает без `<Page>`. Размер панели после этого меняется обычным образом (страницы пересчитываются) |
| Удалить элемент | Удалить его XML-элемент целиком (с вложенными) |
| Переименовать | Изменить `name` |
| Привязка к реквизиту формы | `<DataPath attributeId="N">Имя</DataPath>` (текст — точное имя реквизита из `<Attributes>`) |
| Реквизит формы (добавить, удалить) | в `<Attributes>` добавить `<Attribute id="N" name="Имя">` с `<ValueType …/>`: `String` (с `length`; без — неограниченная), `Number` (`digits`, `fractionDigits`), `Date`, `DateTime`, `Boolean`, ссылка (`kind="Ref"` с `refGuid`), `ValueTable`; реквизит добавляется **сам по себе**, привязка к нему в том же `pack` не нужна. `id` — любой свободный номер реквизитов (нумерация реквизитов отдельная от элементов; номер главного реквизита формы смотрите в `<MainAttribute attributeId>`: `0` у формы из `new-form`, `1` у многих готовых форм), `composite` у `<ValueType>` можно не писать (нет — `false`; `extract` его пишет); пример, который `pack` принимает: `<Attribute id="200" name="Примечание"><ValueType kind="String" length="100"/></Attribute>`, `name` — идентификатор (буквы, цифры, `_`, не с цифры). `<Main>true</Main>` не пишите: так помечаются реквизиты, которые Конфигуратор создаёт для самого элемента, обычный реквизит формы — без него. Удалить реквизит = убрать его `<Attribute>`; пока элемент (поле, таблица, `TypeLink`) привязан к реквизиту, отказ с именем элемента — сначала удалите или перепривяжите элемент (можно в том же `pack`). Строка с `length` пишется строкой переменной длины (как у реквизитов Конфигуратора). Не поддерживается: переименование и смена типа реквизита, к которому привязан элемент; строка фиксированной длины (`fixed="true"`); тип, которого нет в списке выше (кроме `Time`, `ValueTree`, `ValueList`, составной ссылки через `;` в `refGuid` — их `pack` пишет, но в 1С не проверялось); колонки внутри `<Attribute>` (колонки таблицы значений описывает таблица, показывающая реквизит, см. ниже). Если запись `<Attributes>` не читается (лишний тег внутри `<Attribute>`, повтор `id` или `name`, неподдерживаемый `<ValueType>`), список остаётся неизменным, а отказ начинается словами `form attributes:` и называет реквизит и причину. Запись реквизита зависит от версии потока формы (`root[0]`: 19–26 — пять элементов, 27 — шесть); `pack` пишет нужную и после правки проверяет раздел реквизитов потока (число записей, `id` не повторяются и меньше счётчика, привязки полей указывают на существующие реквизиты); форма с неизвестной версией или записью другой длины — отказ. Служебный реквизит `ТаблицаНоменклатуры` формы обработки / отчёта из `new-form` можно удалить, если он не нужен |
| Таблица значений (реквизит формы `ValueTable` с таблицей и колонками) | добавленная `<Table>` с `<DataPath attributeId="N">Имя</DataPath>` (`N`, `Имя` — реквизит `ValueTable`, новый в этом же `pack` или существующий) и `<Columns>`: каждая `<Column name id>` с `<Header>`, `<Width>`, `<ValueType kind=…/>` (`String` с `length` или без, `Number` с `digits` и `fractionDigits`, `Date`, `DateTime`, `Boolean`; нет тега — `String`), `<ReadOnly>true</ReadOnly>`, `<Visible>`, `<Editor>InputField</Editor>` (редактор всегда `InputField`, `extract` пишет его у каждой колонки) и необязательным `<DataPath attributeId="N">Имя.Поле</DataPath>` (поле таблицы значений; нет тега — поле называется как колонка, именно так `extract` показывает путь колонки). Колонки донорской таблицы заменяются вашими, `name` и поле — идентификаторы, `id` — номера колонок внутри таблицы (уникальные). Отказ с причиной: тип колонки `Time`, ссылка, составной, `fractionDigits` больше `digits`; `Events`, `FooterText`, `Tooltip`, `CheckBoxDataPath`, `PictureDataPath`, другой редактор; `Columns` у таблицы, не привязанной ни к табличной части, ни к реквизиту `ValueTable`. Колонки **существующей** таблицы значений (добавить, удалить, перепривязать) не меняются. Без `<Columns>` новая таблица получает две колонки донора |

| Связь длиннее одного шага (`steps`) | `extract` пишет у `<DataPath>` связи из двух и более шагов (`К` ≥ 3 строки в потоке) атрибут `steps="…"`: шаги потока через пробел — `uuid` (`{0,uuid}`), `-N` (стандартный реквизит), `N` (номер свойства платформенного типа), `q:uuid` (колонка регистра бухгалтерии); текст — `Корень.Сегмент.…`, по сегменту на шаг; шаг без известного имени пишется `[токен]` (имя не угадывается: `[0]`, `[-6]`, `[<uuid>]`). Корень `-2` — текущая строка таблицы формы: `ЭлементыФормы.ИмяТаблицы.…`; `-8` у документа — `Движения`, `-60001` — `Отбор`. У колонки таблицы: `<DataPath>` (данные; нет, если шаг не задан), `<CheckBoxDataPath>` (данные флажка) и `<PictureDataPath>` (данные картинки), каждый с `steps`. **Не меняйте `steps` и текст связи из трёх и более шагов — пока отказ** (`editing multi-step links is not supported yet`), так же для `PictureDataPath` колонок и для `CheckBoxDataPath` вне таблицы, привязанной к табличной части (там можно только перепривязать на другую Булево колонку, добавить и удалить колонку, см. «Таблица с табличной частью»), и для нового элемента с `steps` из двух и более шагов; правка прочих свойств такого элемента (`Width`, …) и копия связи из двух строк (`steps` из одного токена — решает текст) работают |
| Привязка к реквизиту объекта | у добавленного или изменённого поля `<DataPath attributeId="N">Корень.Имя</DataPath>`, где `N` и `Корень` — главный реквизит формы (`<MainAttribute>`; у справочника `СправочникОбъект`, у обработки `Объект`), `Имя` — реквизит или стандартный реквизит объекта (`Код`, `Наименование`, `Номер`, `Дата`, …). Имена берутся из метаданных объекта; `extract` показывает тот же текст. Реквизит ссылочного типа привязывается так же (`Корень.Организация`); поля внутри ссылки (`Корень.Организация.Наименование`) не поддерживаются. **Кнопки у добавленного поля ввода** (выбор по типу реквизита проверен только тестами; в живой 1С не проверялось, задача 1.4 изменения `input-field-selection-buttons` открыта): если в XML нет `<ChoiceButton>` / `<OpenButton>`, они берутся по типу реквизита, как в Конфигураторе: справочник и документ — обе кнопки включены; перечисление, план счетов и дата (в том числе стандартный реквизит `Дата`) — только кнопка выбора; число, строка, булево, составной тип — без кнопок (`<ClearButton>` по умолчанию выключена). Чтобы переопределить, задайте тег явно (`<ChoiceButton>false</ChoiceButton>`): написанное в XML всегда главнее; существующих полей и полей, привязанных к реквизиту формы, это не касается. **Новый реквизит объекта**: `pack` берёт реквизиты из XML объекта на диске (имя → uuid), поэтому реквизит можно добавить в `<Объект>.xml` и сразу привязать к нему поле; после `pack` выполните `oneform extract <объект> --replace-generated`, чтобы `src` отразил новые реквизиты (ответ `UNCHANGED` для форм штатный; ключ затирает непринятые правки `src`, поэтому сначала `pack`). Колонка ссылочного типа в таблице, привязанной к табличной части обработки из `.epf`: для редактируемой колонки нужна конфигурация, где описан тип (переменная окружения `ONEFORM_CONFIG_ROOT` — каталог выгрузки конфигурации, иначе конфигурация рядом с `.epf`), иначе пометьте колонку `<ReadOnly>true</ReadOnly>` (ей вид ссылки не нужен) |
| Таблица с табличной частью объекта | добавленная `<Table>` с `<DataPath attributeId="N">Корень.Раздел</DataPath>` и `<Columns>`: каждая `<Column name id>` с `<DataPath attributeId="N">Корень.Раздел.Колонка</DataPath>` (или `…НомерСтроки`), `<Header>`, `<Width>`, `<ReadOnly>true</ReadOnly>` для колонки только для чтения или `<Editor>InputField</Editor>` для редактируемой; в существующей таблице можно **перепривязать** колонку (поменять `DataPath` на колонку того же вида: простой тип на простой, ссылка на ссылку того же вида), **добавить** и **удалить** колонки. Тип колонки берётся из метаданных объекта. **Булево** реквизит привязывается как данные флажка: `<Column>` с `<CheckBoxDataPath attributeId="N">Корень.Раздел.Колонка</CheckBoxDataPath>` вместо `<DataPath>` (`steps` необязателен; если есть, то это uuid колонки), `<ReadOnly>true</ReadOnly>` и `<Visible>false</Visible>` обязательны — так `extract` показывает настоящие колонки флажка; такую колонку можно добавить (в новую и существующую таблицу), удалить и перепривязать на другую Булево колонку той же табличной части. Отказ: `DataPath` у Булево, `DataPath` вместе с `CheckBoxDataPath`, `PictureDataPath`, замена колонки данных на колонку флажка и обратно, строка неограниченной длины, составной тип, замена вида колонки (только чтение ↔ редактируемая, `НомерСтроки`), колонка другой табличной части, таблица значений. Добавление или удаление колонок нельзя сочетать с правкой других колонок в один `pack`: сначала один шаг, затем другой |
| Страницы существующей панели | В `<ChildItems>` панели: **переименовать** — поменять `name` и `<Title>` страницы (дети остаются на ней; при том же числе страниц отличающиеся имена сопоставляются по порядку); **добавить** — новый `<Page name><Title>` (запись и граничные строки копируются с первой страницы этой же панели, область страницы такая же, как у остальных; элементы в добавленную страницу пишите следующим `pack`, не тем же); **удалить** — убрать `<Page>` **вместе со всеми его элементами** (оставшийся на удалённой странице элемент — отказ `moved-control`: переносить элементы между страницами нельзя); **переставить** — поменять `<Page>` местами. Страницы сопоставляются по `name`. `Left/Top/Width/Height` страницы не правьте (область выводится из размера панели); размер панели и состав страниц меняйте разными `pack`. Страницы корневой панели формы так не меняются; панель из одной страницы без закладок и без элементов не показывает `<Page>` и не правится. **`ShowTabs` существующей панели** меняется только между `0` (без закладок) и `1` (сверху) в обе стороны: код и область каждой страницы пересчитываются (`0` → `1`: `1, 19, Width-2, Height-20`; `1` → `0`: `0, 0, Width, Height`; координаты детей страниц не меняются); `Left/Top/Width/Height` страниц не пишите. Отказы (`unsupported-panel`): любой другой код — `<ShowTabs code="2"> of an existing panel: only 0 (None) <-> 1 (Top) is recomputed, the stream holds N; other tab codes (side tabs) change the page area in ways that are not known - set them in the Configurator`; `ShowTabs` вместе с добавлением, удалением или перестановкой страниц в одном `pack` — `<ShowTabs> and the page set (added, removed or reordered pages) cannot change in one pack: change the tabs first, then the pages` (сначала один `pack` на закладки, потом другой на страницы). **Проверено** на панели `ПанельНастроек` настоящего внешнего отчёта (сборка `.erf` платформой и выгрузка: запрос = результат): переименование, добавление (элементы вторым `pack`), удаление пустой и с элементами, перестановка, `ShowTabs` 0 ↔ 1; в живой 1С открыты итоговая форма (2 страницы, закладки сверху, элементы на добавленной странице) и перестановка, `ShowTabs` 1 → 0 в живой 1С не открывали ([functional-report](evidence/functional-report.md)). Новая панель со страницами — в живой 1С ([add-panel-with-pages](evidence/add-panel-with-pages.md)) |
| Размер панели | `Width`/`Height` панели; геометрия страниц пересчитывается сама |
| Кнопки командной панели | В `<Buttons>` панели: порядок элементов = порядок кнопок; `id` — идентичность. Новая кнопка-обработчик: `<Button name="Выполнить" kind="Action" action="ВыполнитьНажатие"><Caption><Item language="ru">Выполнить</Item></Caption></Button>` (`<Tooltip>` по желанию; `id` не нужен, а если задан и в панели его нет — это тоже новая кнопка: настоящий `id` выдаётся следующим за счётчиком панели и виден после `extract`); разделитель: `<Button name="Разделитель" kind="Separator"/>`. **Стандартная команда**: `<Button name="Закрыть" kind="Action" action="Standard:142"/>` (коды — в каталоге ниже; `<Caption>` необязателен: без него подпись берётся из корпуса, например «Закрыть», с ним — ваша; `<Tooltip>` у новой стандартной команды не принимается, подсказку даёт платформа; `actionKind` пишут `Standard` или не пишут). **Подменю**: `<Button name="Действия" kind="Submenu"><Caption><Item language="ru">Действия</Item></Caption><Buttons> ...вложенные кнопки, разделители, подменю... </Buttons></Button>` (действие не указывают; всего до трёх уровней: корень, подменю, подменю в подменю). Кнопку удалить = убрать её элемент (удаление подменю убирает и его кнопки), переставить = поменять элементы местами, **перенести между уровнями** = переписать элемент внутрь другого `<Buttons>` вместе с его `id` (запись кнопки и её действие остаются прежними); в одном `pack` можно сочетать добавление, удаление, порядок, перенос и правку подписей оставшихся кнопок. Имя новой кнопки (и процедуры) — идентификатор, свободный в панели. Процедуру обработчика пишут в `FormModule.bsl` сами: связь только по имени, `pack` при отсутствии `Процедура <Имя>(` печатает предупреждение `warning ...`, но не отказывает. Платформенные подменю (`actionKind="StdSubmenu"`, например «Действия» списка) и кнопки `OpenMovements` можно оставить и переносить целиком, но создавать, удалять и менять их состав нельзя; то же для группы, которую показывают несколько кнопок. Отказ (со строкой `<Button>`): код `Standard:N` без шаблона (в сообщении перечислены поддерживаемые коды), `actionKind` не `Handler` / `Standard` / `Submenu`, `StdSubmenu` и `OpenMovements` у новой кнопки, уровень глубже третьего, картинка / сочетание клавиш / пояснение / `DefaultButton` у новой кнопки, повторное имя |

**Привязки (`Anchors`) добавленных элементов** назначаются автоматически: верх — под ближайшим элементом выше, левый край —
за ближайшим элементом слева (как в Конфигураторе), низ и правый край — размер элемента. Явные `<Anchors>`
(`top="Bottom" topTarget="<id>" topOffset="3"`) учитываются и проверяются. Плавающий элемент без соседей в середине
строки нарушил бы раскладку формы при растягивании окна, поэтому автопривязка важна.
При **удалении** элемента те, кто к нему привязан, перепривязываются к его якорям с сохранением положения в проекте;
поведение при растягивании окна у них может немного измениться.

Добавляются 26 из 27 типов элементов (не добавляется только `ActiveXControl`: для него нет эталона в донорской форме). **`Panel` со страницами** добавляется целиком, вместе с `<Page>` и элементами страниц (строка «Панель со страницами» выше); страницы **существующей** панели меняются отдельной строкой «Страницы существующей панели».
Под `CommandBar` добавлять нельзя: кнопки панели лежат внутри самой панели, а не отдельными элементами; их свойства
правятся в её `<Buttons>`; добавлять, удалять, переставлять и переносить между уровнями подменю кнопки можно (строка «Кнопки командной панели» ниже, каталог `Standard:N` — раздел после таблицы).

**Новая командная панель с кнопками — одним `pack`.** `<CommandBar name="ОсновныеДействияФормы" id="900">` с `Left/Top/Width/Height`, `ZOrder`, `TabOrder`, `<AutoFill>false</AutoFill>` (`<HorizontalAlign>Right</HorizontalAlign>` — кнопки справа) и `<Buttons>` тех же видов, что в строке «Кнопки командной панели»: обработчик (`kind="Action" action="Процедура"` + `<Caption>`), `action="Standard:N"` (например `Standard:142` — «Закрыть»; `<Caption>` необязателен), разделитель (`kind="Separator"`), пользовательское подменю (`kind="Submenu"` с вложенным `<Buttons>`). Порядок элементов — порядок кнопок; `id` кнопок не пишите: они выдаются от счётчика панели из донора (у первой кнопки 31, дальше по порядку; `extract` их покажет). Привязки панели: без `<Anchors>` работает автопривязка; нижняя панель формы, как в Конфигураторе, — `<Anchors top="Bottom" topTarget="900" topOffset="<Top − Height формы>" bottom="Bottom" left="Left" right="Right"/>`, где `topTarget` — тот же `id` (900), что у самой панели в запросе (`pack` подставит выданный, проверено тестом). Чего нельзя: ссылаться на новую панель из **другого** нового элемента того же `pack` (отказ `is another new control of the same edit`: такой элемент добавьте следующим `pack`, целью станет выданный `id`); картинка, сочетание клавиш, `Description`, `DefaultButton`, `ButtonOrder` у новой кнопки; код `Standard:N` без шаблона и платформенные подменю (`StdSubmenu`) — отказ со строкой `<Button>`. Процедуры обработчиков пишите в `FormModule.bsl`, иначе `warning`. Проверено тестами (`extract` упакованного равен запросу: кнопки, порядок, подписи); в живой 1С открытие такой формы пока не проверялось.

## Добавляемые элементы: примеры и рецепты

`attributeId` в `<DataPath>` — `id` главного реквизита формы: число из `<MainAttribute attributeId>` **вашей** формы (`0` в форме из `new-form`, `1` во многих готовых формах; примеры ниже написаны для `0` — подставьте своё число), текст начинается с его имени (`ДокументОбъект.`). `id` — любой свободный, `ZOrder`/`TabOrder` — следующие свободные на странице. Новый элемент можно записать в любое место `ChildItems`, но он всегда окажется **последним** среди соседей (1С хранит элементы в порядке создания и сама переставляет запись: платформа после сборки делает то же); на ряд `ZOrder` это не влияет — задайте его сами, платформа при сборке может перенумеровать слишком большой `ZOrder` (в проверке 30 стало 6). ### Привязки (`Anchors`): атрибуты и рецепты

`<Anchors top="…" bottom="…" left="…" right="…"/>`: значение края — сторона цели, к которой он привязан: `Left`, `Right`, `Top`, `Bottom` или `None` (не привязан); `<край>Target` — `id` цели (нет атрибута — сама форма или панель-контейнер); `<край>Offset` — смещение края элемента от этой стороны цели в пикселях со знаком (вправо и вниз — плюс). Вторая (альтернативная) привязка края — `<край>Alt`, `<край>AltTarget`, `<край>AltOffset` (так `extract` показывает формы Конфигуратора); обычно не нужна. Край, которого в `<Anchors>` нет, получает автопривязку: верх — к нижней стороне ближайшего видимого элемента выше (`top="Bottom" topTarget="<он>" topOffset="<зазор>"`), левый — к правой стороне ближайшего слева (нет соседа — край не привязан), низ и правый край — к собственным верху и левому краю на высоту и ширину (`bottom="Top" bottomTarget="<сам>"`, `right="Left" rightTarget="<сам>"`): размер элемента при растягивании окна не меняется. Соседи ищутся среди элементов, которые уже есть в форме, по их положению **в правленом `Form.xml`** (если в том же `pack` вы сдвинули или растянули существующий элемент — например, подняли `Top` нижней панели, — новый элемент привяжется к тому, что над ним после правки): новые элементы одного `pack` друг к другу не привязываются (в `Anchors` целью может быть только существующий элемент или форма).

* **Поле растягивается вместе с окном**: `<Anchors right="Right" rightOffset="-30"/>`, где `-30` — минус отступ правого края поля от правого края формы, то есть `Left + Width − Width формы` (`Left` 130, `Width` 300 в форме шириной 460: 430 − 460 = −30). Так же в формах Бух.: `Left` 123, `Width` 569 в форме шириной 700 — `right="Right" rightOffset="-8"`. Остальные края остаются автоматическими. Таблица, растущая вниз: `bottom="Bottom" bottomOffset="<нижний край − Height формы>"`. Смещение считается от размера формы в `Form.xml`: изменили размер формы — пересчитайте.
* **Надпись не растягивается**: ничего не писать, автопривязка оставит её ширину и положение; растягивайте только поле рядом.

### Размер формы

`Width`/`Height` корня `Form.xml` меняются (в отчёте `form size`), но **ничего не пересчитывается**: ни командные панели, ни элементы. Пустая форма из `new-form` — `document` 346×262, `catalog-item` 400×85, `catalog-list` 400×300 (`processor`/`report` смотрите в `Form.xml`). В ней `ДействияФормы` (`Top` 0) и `ОсновныеДействияФормы` (`Top` = `Height` − 25) шириной в форму; они привязаны к краям формы, но записанные `Width` и `Top` правьте сами: при размере 460×400 — `Width` 460 у обеих панелей и `Top` 375 у нижней. Эти правки можно делать в том же `pack`, где добавляются элементы: автопривязка новых элементов учитывает правленые координаты.

### `ValueType` у нового поля ввода

Добавленное поле ввода, привязанное к реквизиту объекта (`Корень.Имя`), получает собственный `ValueType` по типу реквизита, как в Конфигураторе: строка с длиной, число с разрядностью, `Date` / `DateTime`, `Boolean`, ссылка на справочник/документ/перечисление конфигурации; для стандартных реквизитов — длина `Код` / `Наименование` справочника и `Номер` документа, `Дата` документа (`DateTime`). Тег `<ValueType …/>` в XML поля главнее; составной тип или тип, которого `pack` не знает, остаётся донорским (`kind="ValueList"`, `extract` показывает его как есть) — задайте `ValueType` явно. Для поля, не привязанного к реквизиту объекта, тип тоже остаётся донорским.

### Подводные камни правки

* **Сначала найдите существующий тег.** `extract` уже показывает `ReadOnly`, `Visible`, `Anchors` и другие теги элемента: меняйте значение в нём, а не вставляйте второй. Дубль — отказ `invalid-xml … duplicate <…> element` (код `FORM_EDIT_REJECTED`).
* **Подписи двуязычные.** У готовых форм (Бух.) в каждом `<Caption>` два `<Item>` — `ru` и `ro`. Правка `ru` оставляет прежний `ro`; новому элементу достаточно `ru`. Нужен и румынский — правьте оба `<Item>`.
* **`Width` не действует, если правый край привязан к другому элементу.** У поля с `<Anchors right="Right" rightTarget="<id>" …/>` смена `Width` меняется в дампе, но на экране размер держит привязка. Поменяйте и привязку (`rightOffset`/`rightTarget` или цель), либо сдвиньте/измените элемент, к которому она привязана.
* **Имя страницы — идентификатор.** `<Page name="…">` добавленной или переименованной страницы: буквы, цифры, `_`, не с цифры (`Страницы.<Имя>` не обращается к другим); иначе отказ `page-name`. Подпись (`<Title>`) — любой текст. Имена уже существующих страниц не проверяются.
* **Процедуру в `FormModule.bsl` пишите перед операторами тела модуля** (раздел «ОПЕРАТОРЫ ОСНОВНОЙ ПРОГРАММЫ»): `pack` проверяет это сам и отказывает (`bsl-procedure-after-body`).
* **Следы работы в каталоге выгрузки конфигурации.** `extract` оставляет в каталоге объекта `src/`, `.oneform/`, `.extract-work/` (замки `*.lock`). Проверено: в список файлов частичной загрузки (`load.sh`, Partial) они не входят; полная загрузка каталога не проверялась — перед ней эти три каталога лучше убрать или не включать.
* **`ReadOnly` у `ChoiceField`** правится, как у `InputField`.

### `FormModule.bsl`

* Кодировка, BOM и переводы строк сохраняются такими, как записаны для этого модуля (`ExtractionManifest.json`); модули Бух. — UTF-8 с BOM. BOM редактора при чтении снимается, лишний не нужен: для UTF-8 без BOM и не ASCII-текста `pack` ставит его сам. LF или CRLF в файле — безразлично.
* В модуле обычной формы реквизиты объекта доступны по имени. Форма документа Бух. `НаправлениеНаВыплату`: `Запрос.УстановитьПараметр ( "Организация", Организация )`, `Общие.глПересчет ( Сумма, Валюта, Курс, … )` (`Организация`, `Валюта`, `Курс` — реквизиты документа; `ДокументОбъект.Валюта` тоже работает). Форма обработки `EFactura`: реквизиты обработки по имени (`Организация`, `НачалоПериода`, `ТипЗаполнения`). Элементы формы — `ЭлементыФормы.Имя`.
* Порядок в модуле: определения процедур и функций должны стоять **перед** операторами тела модуля (раздел «ОПЕРАТОРЫ ОСНОВНОЙ ПРОГРАММЫ»), иначе 1С не создаёт форму: «Определения процедур и функций должны размещаться перед операторами тела модуля». Процедуру, дописанную в конец модуля, который заканчивается операторами тела, `pack` **отказывает** (`bsl-procedure-after-body`, строка процедуры и первого оператора тела): вставьте процедуру перед разделом «ОПЕРАТОРЫ ОСНОВНОЙ ПРОГРАММЫ» (перед первым оператором вне процедур). Объявления `Перем`, комментарии, строки, `#Область` / `#Если` и `&Директивы` оператором тела не считаются; если в исходном модуле нарушение уже было, `pack` его не трогает (отказывает только за то, что внесла правка).

## Если нужной формы ещё нет: `new-form`

```bash
oneform new-form <каталог объекта> --kind <processor|report|catalog-item|catalog-list|document> --name <Имя> [--synonym "Текст"] [--default]
```

Команда создаёт **пустую обычную форму** нужного вида из вшитого шаблона (стандартные командные панели, главный реквизит,
пустой модуль), записывает `Forms/<Имя>.xml` (новый uuid, синоним по умолчанию — имя) и `Forms/<Имя>/Ext/Form.bin`, добавляет
`<Form>Имя</Form>` в `ChildObjects` объекта и выполняет `extract` объекта, так что `src/Forms/<Имя>/Form.xml` готов к правке
(`pack --dry-run` сразу говорит `NO CHANGES`). С `--default` форма становится формой объекта по умолчанию.
Любая ошибка (в том числе `extract`) откатывает все файлы.

| `--kind` | Объект (каталог рядом с `<Имя>.xml`) | Главный реквизит формы | `--default` ставит |
|---|---|---|---|
| `catalog-item` | `Catalogs/<Объект>` (корень `Catalog`) | `СправочникОбъект` | `DefaultObjectForm` = `Catalog.<Объект>.Form.<Имя>` |
| `catalog-list` | `Catalogs/<Объект>` | `СправочникСписок` (таблица списка с колонкой наименования) | `DefaultListForm` |
| `document` | `Documents/<Объект>` (корень `Document`) | `ДокументОбъект` | `DefaultObjectForm` = `Document.<Объект>.Form.<Имя>` |
| `processor` | каталог выгрузки внешней обработки (`epf-dump`, корень `ExternalDataProcessor`) | `ОбработкаОбъект` | `DefaultForm` = `ExternalDataProcessor.<Объект>.Form.<Имя>` |
| `report` | каталог выгрузки внешнего отчёта (`erf-dump`, корень `ExternalReport`) | `ОтчетОбъект` (id 3; форма Конфигуратора: расширение `343b4e00`, `Результат`, `ДействияФормы`, таблица `Отбор`; подпись `Отчет  <Объект>`, 520 × 300) | `DefaultForm` = `ExternalReport.<Объект>.Form.<Имя>` |

Главный реквизит формы хранит идентификатор типа объекта (`TypeId` из `<xr:GeneratedType name="CatalogObject.Имя" ...>` в
`<Объект>.xml`; у списка `CatalogList`, у документа `DocumentObject`, у внешних `ExternalDataProcessorObject` /
`ExternalReportObject`), его команда подставляет сама. Без `GeneratedType` в `<Объект>.xml` команда отказывается.

Что остаётся в пустой форме: у `catalog-item` и `document` панели «ДействияФормы» (автозаполнение) и
«ОсновныеДействияФормы» (OK / Записать / Закрыть), у `catalog-list` таблица списка и «ДействияФормы», у `processor` и `report`
«ОсновныеДействияФормы» с кнопкой «Закрыть», у `report` — как у формы отчёта Конфигуратора: поле табличного документа `Результат`, командная панель `ДействияФормы`
(подменю «Действия» и кнопки «Сформировать» (`Standard:1`), «Конструктор настроек…», «Настройки…», «Сохранить / Восстановить значения…») и таблица настроек `Отбор` (60 колонок, привязка `ОтчетОбъект.[b9754f01-…].[0].[1]` — состав отбора компоновщика настроек отчёта),
настоящих пользовательских элементов нет. Реквизит формы один — главный (`ОбработкаОбъект` у `processor`, `ОтчетОбъект` у `report`); стандартная «Сформировать» в панели ничего не знает о вашем коде (её нажатие в 1С не проверялось); свой обработчик добавьте как обычную кнопку (`<Click>` + процедура в `FormModule.bsl`; через `ОтчетОбъект` доступны экспортные процедуры модуля объекта отчёта).
Форма `report` открывается и у отчёта **без** схемы компоновки (`MainDataCompositionSchema` пуст; проверено в 1С), но таблица `Отбор` связана с компоновщиком настроек и осмысленна
только для отчёта со схемой; `new-form` в этом случае не отказывает и не предупреждает. Ограничения: `.epf` / `.erf` как двоичный файл не поддерживаются — сначала
`epf-dump` / `erf-dump`; имя формы — идентификатор, имя занято — отказ; вид формы должен подходить объекту (справочнику не
подходит `--kind document`).

Форма, созданная Конфигуратором (шаги: объект → «Формы» → «Добавить» → **обычная** форма; для внешней обработки или отчёта
«Файл» → «Новый», закладка «Формы»), по-прежнему работает: сохраните, выгрузите только этот объект (`db-dump-xml`,
`epf-dump` / `erf-dump`), `oneform extract`, правка, `pack`, загрузка (`db-load-xml` и `db-update`, для внешних файлов
`epf-build` / `erf-build`). Если конфигурация на поддержке, перед этим разрешите редактирование объекта (`support-edit`).

## Новая форма у объекта конфигурации

```bash
oneform clone-form <каталог выгрузки>/Catalogs/Контрагенты --from ФормаЭлемента --name ФормаАгента --synonym "Форма агента"
oneform extract <каталог выгрузки>      # новая форма появится в src/Forms/ФормаАгента
```

Пустую форму лучше создавать `new-form` (выше); `clone-form` копирует `Ext/Form.bin` существующей формы объекта, создаёт `Forms/<Имя>.xml` с новым uuid и записывает
форму в `ChildObjects` объекта. Дальше форма правится как обычно (удалить лишние элементы, добавить свои). Исходная форма
выбирается так, чтобы её основной реквизит и данные подходили новой (форма того же объекта). Загрузка такой выгрузки в
базу через `LoadConfigFromFiles` проверена. Каталог объекта можно задать как `.` (имя берётся из каталога). `clone-form` работает с каталогом объекта в XML-выгрузке; для `.epf` сначала `epf-dump`. **Сначала упакуйте свои правки**: после `clone-form` следующий `pack` не пройдёт (`SOURCE_CHANGED`), а `extract` откажет (`GENERATED_FILE_MODIFIED`) и потребует `--replace-generated`, который затрёт непринятую правку. Поэтому `clone-form` отказывается, пока в `src/` объекта есть правки, которые не упакованы (называет файлы). Назначить форму формой по умолчанию (`DefaultObjectForm` и т. п.) нужно
отдельно в XML объекта.

## Каталог стандартных команд (`Standard:N`)

Кнопка `<Button name="..." kind="Action" action="Standard:N"/>` создаёт стандартную команду платформы. Запись команды в потоке
(`{6|7,guid,1,fbe38877-...,{6,srcId,typeGuid,N,{1,вид,группа,код группы,флаг},0,1},0}`) зависит не только от кода: у одного кода
в корпусах УТ 10.3 и Бух. встречается до 30 вариантов (`srcId`, `typeGuid`, группа-источник). `pack` берёт **самый частый вариант
кода для класса формы** (класс — по имени главного реквизита формы: `Документ…` — документ, `Справочник…` — справочник,
`…Список` / `Журнал…` / `…Выбор` — список, иначе — прочая; для класса без собственной строки — самый частый вариант по всем формам) и
поля кнопки (`b2,b3,b5,b8,b9,b11`) по тому же голосованию. Таблица создана скриптом `scripts/mine_standard_commands.py` (результат —
`src/cb_standard.rs`), покрывает все коды, встреченные не менее 10 раз (10 660 стандартных действий). Код без шаблона отклоняется
(`unsupported-button`: `no template for Standard:N; supported codes: ...`). Подпись: `<Caption>` необязателен, без него берётся самый частый
русский текст кнопки из корпуса (у кодов с пустой подписью — пусто, текст даст платформа); `<Tooltip>` у стандартной команды задавать нельзя.
Пока не проверено в 1С: какой из вариантов тела платформа ожидает в конкретной форме (смысл `srcId` не расшифрован) — после

## Форма старой версии потока (25 / 26): что сказать пользователю

Этот раздел — готовый ответ агента. **Не ищи способ конвертации в интернете, не пиши свой конвертер, не правь `Form.bin` вручную, не копируй записи из форм другой версии и не меняй первое число потока.** Всё, что известно, записано здесь; чего не известно, тут сказано прямо.

**Как понять, что форма старая.** Версию показывает отказ `unsupported-stream-version: adding <Вид> to forms of stream version N …` (N = 25 или 26). Отдельной команды, которая печатает версию, пока нет. Форма версии 27 принимает все виды; формы Бух. почти все версии 27, формы УТ 10.3 — смесь 25, 26 и 27.

**Что сказать пользователю (по порядку):**

1. *Что получилось.* Форма записана платформой более старого формата (версия потока 25 или 26). В такой форме `oneform` меняет свойства, удаляет и переставляет существующие элементы, добавляет надпись, поле ввода, флажок и кнопку. Остальные виды (`Table`, `Panel`, `CommandBar`, группа и др.) не добавляются: `pack` отказывает и не трогает форму.
2. *Почему не добавляем.* Записи старого потока устроены иначе: реквизит формы — 5 элементов вместо 6, запись элемента — 10 вместо 16 и т. д. Новые элементы мы берём из форм версии 27. Вставка записи другого формата приводит к тому, что 1С не принимает форму или падает (такое падение мы получали и исправили для четырёх разрешённых видов). Для остальных видов в старом потоке это не проверялось в живой 1С, поэтому мы не угадываем и не пишем.
3. *Что можно сделать (предложи варианты, выбирает пользователь):*
   * **A. Обойтись разрешёнными видами** или правкой свойств существующих элементов.
   * **B. Добавить нужный элемент в Конфигураторе** (достаточно пустого), сохранить; дальше `oneform` правит его свойства и привязки: правка существующих элементов от версии не зависит.
   * **C. Только для внешней обработки или отчёта (`.epf` / `.erf`) — конвертировать форму платформой.** Выгрузка в XML и сборка обратно поднимают версию до 27; после этого доступны все виды элементов. Платформа 8.3 при этом переписывает всю форму целиком.
4. *Чем это грозит (скажи до конвертации):*
   * результат не откроется в платформе, которая не умеет читать формат 27 (на старых платформах **не проверялось** — спроси, на какой платформе работают клиенты);
   * платформа заново записывает всю форму, не только место правки: в пробе изменились идентификаторы и счётчик, подписи стандартных пунктов панели («Подменю», «Действие6»), у части форм появились/исчезли свойства (`LabelPictureLocation`, `StoredData`); модули не изменились. Живой проверкой «всё работает так же» этот результат не подтверждён;
   * для `.epf`/`.erf` выгрузка без базы с конфигурацией теряет ссылочные типы: нужна информационная база с той же конфигурацией;
   * перед конвертацией нужна копия исходного файла; конвертировать только с согласия пользователя.
5. *Как выполнить C (только с согласия; если платформа и база есть — можно сделать за пользователя):*
   * выгрузка: навык `epf-dump` (`powershell.exe -NoProfile -File "~/.agents/skills/epf-dump/scripts/epf-dump.ps1" -InfoBasePath <база> -InputFile <файл.epf> -OutputDir <каталог>`; для `.erf` — `erf-dump`);
   * сборка: навык `epf-build` (`epf-build.ps1`, `erf-build` для отчёта) — собирает новый файл в `build/`; исходный файл не затирай;
   * затем `oneform extract <новый файл>` (для `.erf` — `extract` на каталоге выгрузки) и обычная работа;
   * после `pack` и сборки откройте форму в 1С и проверьте: кнопки панели, подписи, привязки.
   * `1cv8.exe DESIGNER /ConvertFiles` для этого не годится: для файлов формата 8.3 он их не меняет (проверено, [convert-files-experiment](evidence/convert-files-experiment.md)).
6. *Формы внутри конфигурации (справочник, документ, обработка в составе конфигурации).* Вариант C недоступен: выгрузка и загрузка конфигурации версию потока формы не поднимает (проверено на выгрузке УТ платформой 8.3.27: формы остались версии 26). Возможно, версию поднимает открытие и сохранение формы в Конфигураторе, но это **не проверено**. Для таких форм остаются варианты A и B.

## Типичные отказы и что делать

| Сообщение | Причина |
|---|---|
| `FORM_EDIT_REJECTED` (прежде `GENERATED_FILE_MODIFIED`) | отказ правки `Form.xml` / `FormModule.bsl`: `invalid-xml`, `duplicate control name`, `form attributes: …`, `page-name`, `bsl-procedure-after-body`, правка кнопок подменю; файлы не тронуты, код выхода тот же (1). `GENERATED_FILE_MODIFIED` остаётся только там, где изменён сгенерированный файл: `extract` поверх правленого `src/` (нужен `--replace-generated`) и правка файлов-проекций только для чтения |
| `invalid-xml`, `must be one of [...]` | недопустимое значение тега |
| `DataPath '...': the object has no attribute or standard attribute ...` / `several attributes named` / `three or more segments` / `tabular section` / `object metadata not available` | привязка к реквизиту объекта отклонена: неизвестное или неоднозначное имя (в сообщении перечислены доступные), путь из трёх и более частей, табличная часть, либо метаданные объекта недоступны для этой формы; строка и путь названы в сообщении |
| `editing multi-step links is not supported yet` | правка `steps` или текста связи из трёх и более шагов, `PictureDataPath` колонки, `CheckBoxDataPath` вне таблицы с табличной частью (или смена его вида: добавить/убрать/сменить `attributeId`) либо новый элемент с `steps` из двух и более шагов: верните исходные `steps` и текст (строка, элемент и путь названы в сообщении) |
| `Form.xml was extracted by an older oneform (ordinaryFormVersion="2.1", now "2.2")` | `Form.xml` из прежней версии `oneform` не содержит связей из трёх и более шагов: выполните `oneform extract` заново и повторите правку |
| `duplicate control name` (baseline) | в исходной форме есть два элемента с одним именем (≈0,6 % форм УТ): правка XML такой формы не поддерживается, правьте только `FormModule.bsl` |
| `Table ..., Columns: ... a read-only column has no editor` | колонку «только чтение» нельзя сделать редактируемой (`<ReadOnly>false</ReadOnly>` у `<Column>`); `ReadOnly` самой таблицы менять можно |
| `CommandBar ..., Buttons: button action guid missing` / `the patched stream does not hold the requested value` | заголовок кнопки командной панели со стандартным действием менять нельзя |
| `unsupported-button`: `line N: button '...': ...` | новая кнопка командной панели с тем, что не создаётся (код `Standard:N` без шаблона, `StdSubmenu` / `OpenMovements`, подменю глубже третьего уровня, картинка и т. п.), либо удаление / изменение состава платформенного подменю; строка `<Button>` и причина названы в сообщении |
| `unsupported-stream-version`: `adding <Вид> to forms of stream version N is not supported` | в форму потока версии 25 / 26 (и старше) добавляется вид элемента, не проверенный в живой 1С; см. разделы «Версия потока формы и добавляемые элементы» и «Форма старой версии потока (25 / 26): что сказать пользователю» |
| `unexpected-shape` | в потоке встретилась запись неизвестной формы; форма не тронута |
| `layout unsupported (basic)` в отчёте, нет `Form.xml` | форма в формате платформы 8.0 (корень потока `{20`): доступен только модуль |
| `PUBLISH_VERIFY_FAILED` | упакованная форма не воспроизвела запрошенный XML: файлы не тронуты; сообщение перечисляет элементы и свойства. Частая причина — в `ChildItems` переставлены существующие элементы или изменено то, что `pack` не правит (`<#control> added/removed`); место нового элемента среди соседей причиной не бывает |

## Внешний отчёт (`.erf`)

Бинарный `.erf` `oneform` не читает: `extract`, `pack`, `check`, `preview`, `lint` и `validate` пропускают файл и пишут в stderr
`<путь>: пропущен, внешний отчёт: выгрузите в XML (erf-dump), oneform работает с XML-выгрузкой`; если в каталоге больше нечего
обрабатывать, `extract` завершается кодом 2 (`nothing to process`), файл не меняется. Контейнер `.erf` тот же, что у `.epf`, но
корневые метаданные отчёта другие (класс корня `e41aff26-…` вместо `c3831ec8-…`, другой заголовок и другие классы групп реквизитов, форм и
табличных частей), поэтому `.epf`-читатель такой файл отвергает (`METADATA_LAYOUT_UNSUPPORTED`; тест `tests/erf_refusal.rs`, образец
`tests/fixtures/report.erf`, собранный платформой). Рабочий путь: `erf-dump` → каталог с XML → `oneform extract` / правка / `pack` →
`erf-build`. Форма `new-form --kind report` сделана из формы отчёта Конфигуратора (расширение `343b4e00`, главный реквизит `ОтчетОбъект`) и проверена в 1С: [report-form-template](evidence/report-form-template.md).

## Что гарантируется и что проверять в 1С

* Всё, что вы не меняли, сохраняется побайтно; результат проходит повторное декодирование.
* На реальной обработке (188 элементов) правки свойств, добавление и удаление элементов через `oneform` дали в запущенной
  1С ровно ожидаемые отличия свойств всех элементов.
* Для важных изменений откройте форму в 1С и убедитесь визуально (особенно при удалении элементов с зависимыми и при
  добавлении элементов в плотные ряды).

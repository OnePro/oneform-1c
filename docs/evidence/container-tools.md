# Доказательства: container-tools (container-entries, container-diff)

Проверка на реальных файлах владельца, сделана на ветке `container-tools` после этапов A и B (читатель контейнеров, обе команды, указатель владельцев). Эталон: независимый разбор на Python `scripts/container_oracle.py` (свой парсер, без `onec_dtools`). Файлы лежат вне репозитория и в него не копировались.

## Что сверено

`container-diff --json` (сборка `dev`, режим по умолчанию `--by stored`, с `--owners` на выгрузке `upstream/config`) и эталон `container_oracle.py diff` дали одинаковые счётчики и одинаковые списки `differ`, `onlyA`, `onlyB` на всех пяти парах. Тест: `cargo test --test container_tools real_pair_matches_the_oracle -- --ignored` с переменными `ONEFORM_REAL_CF_A`, `ONEFORM_REAL_CF_B`, `ONEFORM_REAL_OWNERS`.

Пример смешанных раскладок: `199_64.cf` — тот же релиз, сохранённый с режимом совместимости 8.3.26 (`version` = 80326, 64-битный контейнер после заглушки 4953 байта). Различаются ровно 4 записи: `84263d9d-970a-4dc5-837d-02d47004ec30` (корневой объект конфигурации), `root`, `version`, `versions`. Остальные 7181 записей побайтно равны записям 32-битного файла: ширина адресов контейнера на сохранённые данные не влияет.

Разбор самого `199_64.cf` (эталон и читатель совпали): записей 7185, третье поле заголовка 7185, оглавление в 3 блоках, 2130 вложенных контейнеров, конец контейнера равен размеру файла (58 650 432 байта).

## Владельцы (`--owners upstream/config`) на паре 199 / ENERGIA

Все записи списков `differ`, `onlyA`, `onlyB` получили владельца. Групп владельцев 23: 20 объектов, `Configuration`, `service` (differ 2) и `unmapped` (differ 1, onlyA 18, onlyB 41). `unmapped` для записей, которых нет в выгрузке `upstream/config` (выгрузка не того релиза), ожидаем: именно поэтому `unmapped` отделён от `service`. Предупреждений о повторяющихся UUID нет. Все первые UUID выгрузки (3488) есть в CF.

Требование «60 МБ и более 7000 записей быстрее 10 секунд» выполнено, но с `--owners` запас небольшой: около 4,6 с уходит на чтение 3489 XML-файлов выгрузки, и это время файловой системы этой машины (обычный обход и чтение тех же файлов в Python заняли 6,2 с). В сборке `dev` та же пара занимает 27–43 с, это ожидаемо для несжатой отладочной сборки.

## Что не сделано и что не проверено

- Пары из процесса команды (A 7185 / `same` 7131 / `differ` 54 / `onlyB` 43; 7226 из 7228 при повторной выгрузке; 4899–4949 из 7123) недоступны: нужны их файлы. Скрипты `cfcmp.py` и `verify_merge.py` получены только как текст. Сверка счётчиков `--by stored` с `cfcmp.py` на их паре не выполнена; вместо неё использован независимый эталон на пяти локальных парах выше. Ближайшее числовое соответствие: пара «выгрузка в CF» с 4912 различиями лежит в их диапазоне 4899–4949.
- 64-битная раскладка без заглушки: образца нет, читается теми же правилами, помечена `layoutVerified=false`.
- Большие конфигурации (сотни МБ) и CF старше 8.3.16 с 64-битным корнем: файлов нет.
- `--by inflated` на четырёх парах CF с CF дал те же счётчики, что и `stored` (записей «только упаковка» нет ни в одной паре); пара с CF из выгрузки этим режимом не прогонялась.
